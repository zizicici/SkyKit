# 新原型与两代旧库的耗时对比

2026-09-22，在 M4 Pro、iOS 26.5 arm64 模拟器中，同一进程单线程实测。
对照为当前仓库的 Astronomy Engine 2.1.19，以及提交 `98aa6b8` 中原样发布的 Go Mooninfo 二进制。
原型与 Astronomy Engine 使用 `-O3`，不启用 LTO；Go 库沿用原构建，不假设其编译选项相同。

每项预热 20 次、测试 7 批，轮换库的执行顺序，取批次中位数。
求下次月相每批 300 次，其他项目每批 3,000 次。结果参与校验和，防止优化器删除计算。
双方每次收到新的时间结构，避免跨调用复用 Astronomy Engine 的时间缓存。

## 连续日期

使用相邻 8.64 秒的 1,000 个日期，覆盖约 2.4 小时；短周期方向调用场景。
单位为**微秒／次**，越小越快。

| 工作 | 新 DE440 原型 | Astronomy Engine | 原 Go Mooninfo |
| --- | ---: | ---: | ---: |
| 月相角 | 0.36 | 0.56 | 无对应公开接口 |
| 照亮比例 | 0.18 | 0.35 | 58.67 |
| 查找指定的下一次主要月相 | 18.20 | 4.88 | 619.50 |
| 地平方向，无大气折射 | 10.46 | 0.38 | 无对应公开接口 |

新原型相对 Astronomy Engine：月相角约快 1.5 倍，照亮比例约快 1.9 倍；
下次月相约慢 3.7 倍，地平方向约慢 27.5 倍。相对 Go Mooninfo，可比的照亮比例约快 326 倍，
下次月相约快 34 倍；Go 数值包含原有语言桥接和运行时成本。

## 分散日期

打乱约 2020–2030 年间的 1,000 个日期，模拟读取不同年份照片等工作：

| 工作 | 新 DE440 原型 | Astronomy Engine | 原 Go Mooninfo |
| --- | ---: | ---: | ---: |
| 月相角 | 0.40 | 0.75 | — |
| 照亮比例 | 0.20 | 0.51 | 80.93 |
| 下一次主要月相 | 17.13 | 5.94 | 669.57 |
| 地平方向 | 23.01 | 0.52 | — |

因此不能把连续日期测得的约 10 微秒当作所有输入的恒定耗时，也不能说新算法全面快于旧库。
当前 App 每秒更新一次天文方向，连续日期下原型核心每秒耗时约 0.01 毫秒，
由这个基准推算的单核计算占用约 0.001%；不包括相机、传感器、UI 或系统调度。

## 可比范围

比较的是相同用途，不是相同精度：新原型采用完整 IAU 2006/2000A 转换、迭代光行时、
有限距离太阳偏折和更严格的事件求根。新求根数值终止条件为 0.1 毫秒，Astronomy Engine 为 0.1 秒；
这些容差不是绝对天文精度。两套实现的月球模型、方向修正和求根策略不同。

时间转换、星历加载、首次 Go 运行时启动、Swift 锁、UI 和旧月相表查询均未计时。
数据已在内存中；本次不是冷启动、峰值内存或真机耗电测试。
时间输入预先准备，使用 Astronomy Engine 的 TT 估算，并取 TDB≈TT；该近似仅用于性能测试。
原来的预计算月相表属于直接查询，不能用这里的事件求根耗时代表其查询性能。

重现：先按 README 构建原型并启动 arm64 模拟器，然后运行：

```sh
python compare_libraries.py --simulator <UDID>
```

参考数据、编译参数、原始批次耗时和 SHA-256 见 [library-benchmark-results.json](library-benchmark-results.json)。
旧库只提取到缓存目录，不恢复或改动工作区内已删除的框架文件。
